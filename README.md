# YoloTrtCuda


**High-speed YOLO object-detection inference library for TensorRT and CUDA, focused on fast preprocessing, inference, and postprocessing. It depends only on TensorRT, CUDA, and cuDNN, and does not depend on OpenCV.**

`YoloTrtCuda` is an object-detection library for CUDA/TensorRT that provides model conversion, inference, and postprocessing.
It intentionally contains only the object-detection module; classification, segmentation, pose, and OBB modules are not included.

English | [中文文档](docs/README-Chinese.md)

The public C++ API, `DetectResultBox`, image-view structures, and calling sequence are kept consistent with
[YOLO-ONNXRuntime-DirectML](https://github.com/xxmzwf/YOLO-ONNXRuntime-DirectML), with the class name changed to
`YoloTrtCuda`. It also provides `setDevice(int device)` for selecting a CUDA GPU.

Key features:

- Uses TensorRT for model inference; regular inputs use CUDA preprocessing, baked inputs use CPU SIMD resize/letterbox, and output decoding plus NMS are completed with CPU SIMD.
- Confidence and NMS thresholds are configured only at runtime and are not embedded in the engine.
- Uses `tools/onnx_to_yolotrtcuda.py` to generate the dedicated FP16 engine container.
- Ordinary TensorRT `.engine` files are rejected rather than loaded; the dedicated conversion script is required.
- Installation includes only `YoloTrtCuda` headers, the shared library, import library, and CMake configuration; TensorRT, CUDA, and cuDNN DLLs are not copied.

## Supported scope

This project supports YOLOv3 through YOLO26, as well as some export forms of variants such as YOLO-World, YOLOE, and YOLO-Master. It handles only the raw object-detection output path, so actual compatibility also depends on whether the ONNX model can be exported with a single input and one or more compatible raw detection heads.

| Model type | Typical raw output | YoloTrtCuda |
| --- | --- | --- |
| YOLOv3–YOLOv7 and YOLOv5-style | `[1, N, 4+1+C]`, including objectness | Supported; custom class counts can use `--objectness on` |
| YOLOv8, YOLOv9, YOLOv11, and YOLOv12-style | `[1, 4+C, N]` or equivalent `[1, N, 4+C]`, without objectness | Supported |
| YOLOX-style raw head | `[1, N, 4+1+C]`, with regression values decoded by stride | Supported; the conversion script detects `reg_preds/obj_preds/cls_preds` and uses YOLOX decoding |
| YOLOv10 and YOLO26 end-to-end exports | Commonly `[1, N, 6]`, with NMS already performed inside the model | Not directly supported; export the raw detection head |
| YOLO-World, YOLOE, YOLO-Master, and other variants | Depends on the exported graph | Supported only when the output matches one of the raw detection formats above; additional open-vocabulary postprocessing is not included |

The conversion script automatically bakes the input as `UINT8 NHWC`. In baked mode, transpose, type conversion, and normalization are placed in the TensorRT graph, while resize and letterbox are handled by the runtime's CPU SIMD path.

The following are outside the scope of this library:

- Segmentation, pose, OBB, classification, and models with auxiliary non-detection outputs;
- Engines that already contain EfficientNMS or other NMS/threshold postprocessing;
- Ordinary TensorRT engines;
- Inference with a runtime batch size greater than 1;
- Models whose input is not a single floating-point NCHW image tensor or the UINT8 NHWC image tensor generated by this project's baking process.

The class count does not have to be the 80 COCO classes, but the output layout must match the script's `--objectness` setting.
The library returns numeric class IDs only and does not read a class-name file.

For ordinary YOLO raw heads, input preprocessing scales pixels to `[0, 1]` by default. For automatically detected YOLOX raw heads, the library uses the common YOLOX floating-point input range `[0, 255]` and performs grid decoding with strides 8, 16, and 32 during CPU postprocessing.

## Requirements

The current CMake configuration and local validation environment are:

- Windows x64;
- Visual Studio/MSVC with C++17;
- CMake 3.18 or later;
- CUDA 13.3;
- TensorRT 11.2;
- cuDNN 9.24.

The project uses the following paths by default, but all of them can be overridden with CMake parameters:

~~~text
D:/Code/Libs/TensorRT-Shared
C:/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v13.3
C:/Program Files/NVIDIA/CUDNN/v9.24
~~~

`CUDNN_PATH` is used to check and record the development environment; YoloTrtCuda itself does not link against or copy cuDNN DLLs into the install directory.
Deployment still requires you to provide the TensorRT, CUDA, and cuDNN runtime DLLs on the target machine and make them available through the system `PATH` or another location searchable by the application.

## Build and install

This project builds a shared library. With the Visual Studio multi-configuration generator, `Release` is selected through `--config Release` and is the default build configuration in this document.

Run the following commands from the project root:

~~~powershell
cmake -S . -B build `
  -DCMAKE_BUILD_TYPE=Release `
  -DTENSORRT_PATH="D:/Code/Libs/TensorRT-Shared" `
  -DCUDAToolkit_ROOT="C:/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v13.3" `
  -DCUDNN_PATH="C:/Program Files/NVIDIA/CUDNN/v9.24"

cmake --build build --config Release --parallel 8
cmake --install build --config Release --prefix "D:/Code/Libs/YoloTrtCuda"
~~~

If CMake does not find NVCC automatically, you can additionally specify:

~~~powershell
-DCMAKE_CUDA_COMPILER="C:/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v13.3/bin/nvcc.exe"
~~~

To compile only for a specific GPU architecture, specify it during configuration, for example:

~~~powershell
cmake -S . -B build `
  -DCMAKE_BUILD_TYPE=Release `
  -DCMAKE_CUDA_ARCHITECTURES="86" `
  -DTENSORRT_PATH="D:/Code/Libs/TensorRT-Shared" `
  -DCUDAToolkit_ROOT="C:/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v13.3" `
  -DCUDNN_PATH="C:/Program Files/NVIDIA/CUDNN/v9.24"
~~~

The default architectures are `75;86;89;90`. If CUDA or TensorRT is installed elsewhere, replace the corresponding CMake parameters.

The install directory has the following structure:

├── bin/
│   └── YoloTrtCuda.dll

## Using the library in your CMake project

Assuming the install prefix is `D:/Code/Libs/YoloTrtCuda`, configure the downstream project as follows:

~~~cmake
list(APPEND CMAKE_PREFIX_PATH "D:/Code/Libs/YoloTrtCuda")

find_package(YoloTrtCuda CONFIG REQUIRED)

add_executable(my_detector main.cpp)
target_link_libraries(my_detector PRIVATE YoloTrtCuda::YoloTrtCuda)

# Copy this library's DLL next to the downstream program.
add_custom_command(TARGET my_detector POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_if_different
            ${YoloTrtCuda_RUNTIME_DLLS}
            "$<TARGET_FILE_DIR:my_detector>"
    VERBATIM)
~~~

You can also pass the install prefix during configuration:

~~~powershell
cmake -S . -B build `
  -DCMAKE_PREFIX_PATH="D:/Code/Libs/YoloTrtCuda"
cmake --build build --config Release
~~~

The downstream application must also deploy third-party DLLs matching the TensorRT/CUDA/cuDNN versions used to build the library. They can be placed next to the application or added to the system `PATH`. This library's CMake package does not copy those dependencies for downstream projects.

## Convert ONNX to a dedicated FP16 engine

The conversion tool is [tools/onnx_to_yolotrtcuda.py](tools/onnx_to_yolotrtcuda.py). It:

1. Checks whether the ONNX model has one input and one or more rank-3 raw detection outputs; if both a final concatenated output and intermediate feature heads are exposed, it keeps only the final detection output;
2. Automatically bakes a floating-point NCHW input as UINT8 NHWC and adds transpose, Cast, and normalization nodes to the graph;
3. Converts the model to FP16;
4. Builds the engine with TensorRT;
5. Writes the `YoloTrtCuda` container header and model metadata around the engine.

For YOLOX-style raw heads, the script records objectness, YOLOX grid decoding, and the input pixel range in the metadata. After the runtime loads the engine, it automatically selects the corresponding preprocessing and postprocessing behavior.

All compatible raw detection outputs are bound to TensorRT. The runtime merges their candidate boxes and performs one NMS pass.
All detection heads must use the same class layout; EfficientNMS or other threshold postprocessing inside the model remains outside the scope of this library.

The output file is therefore not a regular `.engine` that can be passed directly to an ordinary TensorRT program, and it is not the output of a regular `trtexec --saveEngine` command.

### Install Python dependencies

You need a TensorRT Python wheel matching the local Python version, plus `onnx`, `onnxruntime`, and `numpy`.
The example below uses a Python 3.11 wheel; choose the corresponding wheel if you use another Python version:

~~~powershell
py -3 -m pip install onnx onnxruntime numpy
py -3 -m pip install "D:/Code/Libs/TensorRT-Shared/python/tensorrt-11.2.1.2-cp311-none-win_amd64.whl"

# If the TensorRT Python runtime cannot find its DLLs, extend PATH in the current PowerShell session.
$env:PATH = "D:/Code/Libs/TensorRT-Shared/bin;$env:PATH"
~~~

### Export and convert

First export a raw YOLO ONNX model without NMS. For example, with Ultralytics:

~~~powershell
yolo export model=models/yolo11n.pt format=onnx batch=1 imgsz=640
~~~

Then run this project's conversion script. When only an ONNX file is provided, the script automatically performs model baking and FP16 conversion and writes `<input-file-name>_fp16_u8.engine` in the same directory. For example:

~~~powershell
py -3 tools/onnx_to_yolotrtcuda.py models/yolo11n.onnx
~~~

The command above generates `models/yolo11n_fp16_u8.engine`. The script prints progress for each conversion stage; TensorRT engine building may take some time. YOLOX raw heads automatically retain their common `0..255` input range and are not divided by 255 again. Models that are already `UINT8 NHWC` can also be passed directly to the script.

For a YOLOv5-style model with a custom class count, if the script cannot infer objectness from the output dimensions, specify it explicitly:

~~~powershell
py -3 tools/onnx_to_yolotrtcuda.py models/custom_yolov5.onnx `
  --objectness on
~~~

The main supported parameters are:

| Parameter | Description |
| --- | --- |
| `INPUT` | Raw or already-baked YOLO ONNX file; output is saved automatically as `<input-file-name>_fp16_u8.engine` in the same directory |
| `--height`, `--width` | Input dimensions used for building; default is 640×640 |
| `--objectness auto\|on\|off` | Whether to parse objectness in the YOLOv5 style; default is `auto` |
| `--workspace-gb` | TensorRT workspace limit |
| `--verbose` | Print detailed TensorRT logs |

This project deliberately does not use EfficientNMS postprocessing because it would bake the threshold and NMS configuration into the engine.
Output decoding and NMS are performed on the CPU here, and the NMS threshold is set through the runtime API. Ordinary TensorRT engines generated by other tools cannot be used directly as YoloTrtCuda inputs.

## API

The header is [YoloTrtCuda/include/YoloTrtCuda.h](YoloTrtCuda/include/YoloTrtCuda.h).

### Public data structures

~~~cpp
struct DetectResultBox {
    float x;
    float y;
    float width;
    float height;
    float score;
    int classId;
};
~~~

`x` and `y` are the top-left coordinates; `width` and `height` are the dimensions. Coordinates are expressed in pixels of the original input image.

~~~cpp
enum class ImageFormat {
    BGR8,
    RGB8,
    BGRA8,
    RGBA8,
    GRAY8
};

struct ImageView {
    const void* data = nullptr;
    int width = 0;
    int height = 0;
    int channels = 0;
    std::size_t stride = 0;
    ImageFormat format = ImageFormat::BGR8;
};
~~~

### Method reference

| Method | Description |
| --- | --- |
| `bool setModel(std::string path)` | Loads a YoloTrtCuda-specific engine; returns `true` on success |
| `void setDevice(int device)` | Selects the CUDA GPU. Call it before `setModel` when possible; if a model is already loaded, changing the device reloads it |
| `void setConfidenceThreshold(float value)` | Sets the runtime confidence threshold |
| `void setNMSThreshold(float value)` | Sets the runtime IoU NMS threshold |
| `void setImage(ImageView& image)` | Sets the current image view; the library does not own the image memory |
| `void preprocess()` | Performs format conversion, resize, and letterbox; baked inputs use CPU SIMD to produce UINT8 NHWC |
| `void infer()` | Runs inference with TensorRT |
| `void postprocess()` | Copies outputs, decodes candidate boxes, and runs NMS |
| `std::vector<DetectResultBox> resultBoxes()` | Returns a copy of the current results |

The typical call sequence is:

~~~text
setDevice -> setModel -> setImage -> preprocess -> infer -> postprocess -> resultBoxes
~~~

### C++ example

The example below uses OpenCV to read a BGR image. OpenCV is not a public dependency of YoloTrtCuda; it is only the image source used in this example:

~~~cpp
#include <YoloTrtCuda.h>
#include <opencv2/imgcodecs.hpp>

#include <iostream>

int main() {
    cv::Mat frame = cv::imread("image.jpg", cv::IMREAD_COLOR);
    if (frame.empty()) {
        return 1;
    }

    YoloTrtCuda detector;
    detector.setDevice(0);

    if (!detector.setModel("models/yolo11n.yolotrtcuda.engine")) {
        std::cerr << "failed to load model\n";
        return 1;
    }

    detector.setConfidenceThreshold(0.40f);
    detector.setNMSThreshold(0.45f);

    ImageView image;
    image.data = frame.data;
    image.width = frame.cols;
    image.height = frame.rows;
    image.channels = frame.channels();
    image.stride = frame.step;
    image.format = ImageFormat::BGR8;

    detector.setImage(image);
    detector.preprocess();
    detector.infer();
    detector.postprocess();

    for (const DetectResultBox& box : detector.resultBoxes()) {
        std::cout << "class=" << box.classId
                  << " score=" << box.score
                  << " box=(" << box.x << ", " << box.y
                  << ", " << box.width << ", " << box.height << ")\n";
    }

    return 0;
}
~~~

`ImageView` only stores the external image pointer. The image data must remain valid while `preprocess()` is running; after preprocessing, the library copies the data into its own GPU buffer.

## Performance and deployment notes

During inference, TensorRT uses a dedicated CUDA stream; regular input preprocessing uses CUDA kernels, while baked input uses CPU SIMD resize/letterbox. `infer()` contains only the TensorRT enqueue and its synchronization; the output D2H copy, candidate-box decoding, and NMS are all completed in `postprocess()`. No threshold or NMS layer is appended to the TensorRT network.

As a result, runtime thresholds can be adjusted without changing the main engine, while configurable postprocessing stays outside the TensorRT graph. Actual throughput and latency still depend on the GPU, input size, model architecture, TensorRT version, and batch configuration; this README does not provide performance numbers that have not been measured.

At minimum, deployment requires:

- The application itself;
- `YoloTrtCuda.dll`;
- TensorRT, CUDA, and cuDNN DLLs matching the build;
- A `.yolotrtcuda.engine` file generated by this project's script.
